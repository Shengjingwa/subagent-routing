# Subagent routing

Each time you dispatch a subagent (Cursor: `Task` tool; Claude Code: `Agent` tool; Codex: `spawn_agent`), choose its model in two steps. First, pick the tier by task type (see below). Second, on that tier's line, look only at models of your own model family (for example, `claude-…`, `opus`, `sonnet`, and `haiku` are Claude; `gemini-…` is Gemini). If the line has a model of your family, set the subagent's model to it and treat this as an explicit user request for it. If the line has none, or shows a placeholder in angle brackets, do not set a model, so that the subagent inherits your model. Never take a model of another family from the tier table, even when it is the only model on the line. If the user names a model in a chat message (the tier table does not count), use that model for the work they named it for, also when it is of another family; your other dispatches still follow the tier table. The only other case for another family is a running skill that asks for models of different vendors (see the details file).

If you are a subagent yourself, skip the split announcement and the delegation of strong-tier work, and dispatch subagents only when your prompt asks you to. Still use the report format that your prompt asks for.

Tier table (models appear only here; to change a model, change only these three lines). A line can list one model or comma-separated models of different families:
- Light: `{{LIGHT_MODEL}}`
- Standard: `{{STANDARD_MODEL}}`
- Strong: `{{STRONG_MODEL}}`

Your strong-tier model is the model of your family on the Strong line. If that line has no model of your family, you are the strong-tier model. For example, if you run as Gemini and the Strong line lists only Claude models, you are the strong-tier model, and strong-tier subagents inherit your model. If any tier still shows a placeholder in angle brackets, remind the user once per session to fill in the table.

Pick the tier by task type. When you are not sure between Light and Standard on read-only work or running commands, start with Light; when you are not sure between Standard and Strong on code changes, verification, or analysis, use Standard, and reserve Strong for open-ended design and hard root-cause diagnosis:
- Light: read-only lookups, routine code/git/log scouting, or running existing commands and scripts. Examples: locate files, symbols, settings, or citations in docs, scout code paths, `git log -S` / `blame`, or logs (including `explore`), pull facts from many files or repositories, look up product or tool documentation (such as `cursor-guide`), extract given facts from known web pages, or run an existing script, test, evaluation, or API/Git query and collect the output or error lines.
- Standard: work that needs synthesis, rubric-based verification, independent reviews, or code changes where the design is already decided. Examples: trace and explain complex cross-module flows, grade items against a fixed rubric, fact-check a report's numbers or claims against local files, summarize research, triage CI failures, test in a browser, follow MRs and fix routine pipeline/review issues, implement an already-decided change (including running offline evaluations on it and applying reviewer or user feedback), and first-pass or incremental independent code, spec, and security reviews.
- Strong: open-ended design, hard root-cause diagnosis, and code that must make its own design decisions.

When to dispatch: do targeted lookups and one-shot local script or query runs yourself (a known file, symbol, or database, 2-3 files, one search, or one command). Also do design and diagnosis that depend on the conversation yourself, unless your own model is not the strong-tier model (see "Split the work"). Dispatch broad searches, work that would fill your context, and work that can run in parallel; do not dispatch a review subagent unless the user or a running skill asks for one. Start independent subagents together, at most 4 at a time; for batch grading or evaluation, group items into at most 4 subagents or one local script so each item does not wake you separately, and tell each subagent to write its results to a file about 20 items at a time, so that no message gets too long and a failed run keeps its finished items. Run work whose result you do not need yet in the background, including when you still have your own files to write in the turn or when running several long or cross-family subagents in parallel so one slow or blocked run does not hold up the rest.

Split the work: for a task that changes 2 or more files or needs more than one line of investigation, first say in one or two sentences what you do yourself, what you dispatch in parallel, and what goes to the background. Then start; do not wait for confirmation. If your own model is not the strong-tier model, dispatch all strong-tier work (design, root-cause diagnosis, also when it depends on the conversation) to a strong-tier subagent, and put the background it needs in its prompt.

In each dispatch prompt, tell the subagent to give the conclusion first, then the evidence (file:line, commands and their output), then what it did not find or is not sure about. For a list that must be complete, it also returns the commands it used and the total count. Bound read-only scouting to 2-3 tool rounds in the prompt (also before writing a file or plan, and say that such a task is done once the file is written and checked once; for `explore`, set thoroughness to `quick` or `medium`), tell the subagent to use native file-reading and search tools in parallel when the files are in a clean checkout, and tell it to pair any progress update with a real tool call. Tell it to put the complete answer in its final message, because you receive only that message. In your progress notes, say which model each subagent used and whether you ran it again at a higher tier.

Before you use a subagent's conclusion to change code or to tell the user a result, check 1-2 key pieces of its evidence yourself. If the conclusion is "not found" or "does not exist", check again yourself or run it again one tier up. If a subagent stops on a provider or connection error, send that same subagent a follow-up instead of starting a new one (Cursor: pass its full 36-character Agent ID as `resume`), so that it keeps the work it has done. Read `{{DETAILS_PATH}}` first when a subagent result is not acceptable and you need to run it again, when a running skill prescribes how to dispatch subagents, when the user asks to change the tier table, or when the tier table and the models you can dispatch do not agree (a tier's model is missing, or a newer version of the same model family is available).
