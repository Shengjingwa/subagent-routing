# Subagent routing

Each time you dispatch a subagent (Cursor: `Task` tool; Claude Code: `Agent` tool; Codex: `spawn_agent`), pick its tier from the tier table below. A tier line can list one model or comma-separated models from different model families (for example, Claude and Gemini). If the chosen tier lists a model in your own model's family, set the subagent's model to that model and treat this as an explicit user request for it. If the chosen tier has no model in your family (or shows a placeholder in angle brackets), do not set a model, so that the subagent inherits its default model. If the user names a different model in the conversation, use that model for that dispatch.

If you are a subagent yourself, skip the split announcement, the delegation of strong-tier work, and the review before delivery, and dispatch subagents only when your prompt asks you to. Still use the report format that your prompt asks for.

Tier table (models appear only here; to change a model, change only these three lines):
- Light: `{{LIGHT_MODEL}}`
- Standard: `{{STANDARD_MODEL}}`
- Strong: `{{STRONG_MODEL}}`

If the strong tier lists a model in your family, that model is the strong-tier model; otherwise treat your own model as the strong-tier model. If any tier still shows a placeholder in angle brackets, remind the user once per session to fill in the table.

Pick the tier by task type. When you are not sure between Light and Standard on read-only work or running commands, start with Light; when you are not sure between Standard and Strong on code changes, verification, or analysis, use Standard, and reserve Strong for open-ended design, hard root-cause diagnosis, and first-pass independent reviews:
- Light: read-only lookups, routine code/git/log scouting, or running existing commands and scripts. Examples: locate files, symbols, settings, or citations in docs, scout code paths, `git log -S` / `blame`, or logs (including `explore`), pull facts from many files or repositories, look up product or tool documentation (such as `cursor-guide`), extract given facts from known web pages, or run an existing script, test, evaluation, or API/Git query and collect the output or error lines.
- Standard: work that needs synthesis, rubric-based verification, or code changes where the design is already decided. Examples: trace and explain complex cross-module flows, grade items against a fixed rubric, fact-check a report's numbers or claims against local files, summarize research, triage CI failures, test in a browser, follow MRs and fix routine pipeline/review issues, implement an already-decided change (including running offline evaluations on it and applying reviewer or user feedback), and re-review incremental fixes after an initial Strong review.
- Strong: open-ended design, hard root-cause diagnosis, first-pass independent code, spec, and security review, and code that must make its own design decisions.

When to dispatch: do targeted lookups yourself (a known file or symbol, 2-3 files, or one search). Also do design and diagnosis that depend on the conversation yourself, unless your own model is not the strong-tier model (see "Split the work"). Dispatch broad searches, work that would fill your context, work that can run in parallel, and reviews that need a fresh context without your assumptions. Start independent subagents together, at most 4 at a time. Run work whose result you do not need yet in the background.

Split the work: for a task that changes 2 or more files or needs more than one line of investigation, first say in one or two sentences what you do yourself, what you dispatch in parallel, and what goes to the background. Then start; do not wait for confirmation. If your own model is not the strong-tier model, dispatch all strong-tier work (design, root-cause diagnosis, review, also when it depends on the conversation) to a strong-tier subagent, and put the background it needs in its prompt.

Review before delivery: when a change spans more than one file, or touches security, data, or a release, dispatch one strong-tier subagent for an independent review before you deliver. Give it only the diff, the goal, and the acceptance criteria. Fix the problems that you confirm and run the checks again. Put doubtful points and proposed design changes in your delivery note. Do not do this review for small changes (a few lines that do not touch security, data, or a release, even if they span files), or when a running skill has its own review step.

In each dispatch prompt, tell the subagent to give the conclusion first, then the evidence (file:line, commands and their output), then what it did not find or is not sure about. For a list that must be complete, it also returns the commands it used and the total count. Tell it to put the complete answer in its final message, because you receive only that message. In your progress notes, say which model each subagent used and whether you ran it again at a higher tier.

Before you use a subagent's conclusion to change code or to tell the user a result, check 1-2 key pieces of its evidence yourself. If the conclusion is "not found" or "does not exist", check again yourself or run it again one tier up. Read `{{DETAILS_PATH}}` first when a subagent result is not acceptable and you need to run it again, when a running skill prescribes how to dispatch subagents, when the user asks to change the tier table, or when the tier table and the models you can dispatch do not agree (a tier's model is missing, or a newer version of the same model family is available).
